# 第一阶段架构审查

## 审查决定

| 问题 | 第一阶段规则 |
| --- | --- |
| “全部使用 UUID”与预置商店 ID 冲突 | 预置 ID 使用 `heb`、`wholefoods`、`99ranch`。自定义商店和其它实体使用本地 UUID。别名和显示名可修改。 |
| 多个活动行程可能争用同一需求 | 不同商店可同时购物。每家商店最多一个活动行程，每条需求最多关联一个行程。打开、分配、勾选、关闭均在事务中检查最新数据。 |
| “优先”与“仅限”在跨店时缺少区分 | 任意商店、匹配的优先或指定商店进入默认候选。未匹配的优先项需开启跨店候选并显式选入。未匹配的指定项须先更改商店规则。 |
| 停用商店可能使历史引用或待购规则失效 | 通过 `archivedAt` 停用并保留原 ID。活动行程存在时先结束行程。仍有需求只能在这家商店购买时先调整需求。 |
| “重复导入”与“同名需求”语义不同 | 按规范化后的条目集合做 SHA-256，保留条目出现次数，忽略条目、字段及商店 ID 的顺序。已成功提交的批次默认拒绝。同名活跃项和批内同名项会提示。 |
| 合并可能丢失来源、规格或备注 | 仅待购项、同名、同规则、同来源、同备注、同可选标记，并且均缺数量或同单位时提供合并。由用户确认。目录商品及行程中的需求保留独立记录。 |
| 恢复和普通导入用途不同 | 交换输入、未购导出、完整备份分别使用 `shopping-import`、`shopping-outstanding`、`shopping-backup`。完整备份先校验引用与状态，再经两次确认事务覆盖。 |
| GitHub Pages 仓库子路径可能共享来源 | IndexedDB 按来源隔离。独立数据库名将应用数据分开，但同一来源的其他代码也能打开该数据库。两项目对接约定使用 JSON 边界。 |

商品购买状态由 `Need` 单独保存。数量未知用 `null`。显式数量须为有限正数，单位必填。取消购买保留 `cancelled` 记录。复购生成新的 ID。备份包含记录修订、删除标记（存在时）和批次指纹。设备标识留在当前浏览器，恢复沿用备份的数据集标识。

## 数据库设计

独立数据库 `home-shopping-list-v1`，IndexedDB 版本 1。记录以 `id` 为键。

| 表 | 主键、引用和索引 |
| --- | --- |
| `stores` | 预置字符串 ID 或 UUID。包含名称、别名、停用时间。 |
| `products` | UUID，可空的商品目录。保留名称、别名和分类。 |
| `needs` | UUID。引用可空的 `products.id`、条件性关联的 `trips.id` 及规则中的 `stores.id`。索引 `state`、`tripId`。 |
| `trips` | UUID。引用一个 `stores.id`。索引 `storeId`、`status`。 |
| `importBatches` | UUID。索引非唯一的 `fingerprint`，记录新增、合并和跳过数量，允许显式重复导入。 |
| `appMeta` | 固定记录键 `dataset`，包含 `datasetId`、`deviceId` 和当前数据快照令牌。 |

每次写入在同一事务内读取当前数据并应用变更，等待事务提交后才显示成功。导入、行程计划、关闭及恢复使用快照令牌，遇到并行变更要求重新预览或刷新确认。IndexedDB 升级按 `oldVersion` 递增，备份 `schemaVersion` 和交换协议 `version` 各自独立。v1 适用于个人清单规模，事务读取当前小型数据集供规则校验。

## 状态转换

| 原状态 | 操作与条件 | 结果 |
| --- | --- | --- |
| 无 | 新建、导入或显式复购 | `pending`，无行程和购买时间 |
| `pending` | 确认加入匹配规则的活动行程 | `planned`，设置 `tripId` |
| `planned` | 在关联的活动行程内勾选 | `purchased`，设置 `purchasedAt` |
| `purchased` | 关联行程仍活动时取消勾选 | `planned`，清空 `purchasedAt` |
| `planned` | 留待下次或关闭行程 | `pending`，清空 `tripId`，保留商店规则 |
| `pending` 或 `planned` | 取消购买 | `cancelled`，清空 `tripId` |
| `purchased` | 关闭行程 | 保持已购，保留来源行程和购买时间 |

## 协议与模块

[TypeScript 数据契约](../src/domain/model.d.ts) 和 [Import Contract v1 JSON Schema](shopping-import.schema.json) 可供菜谱项目接入。运行时校验还检查当前商店、单位和文本规范化、文件大小以及来源引用冲突。导入允许最多 500 项或 1 MiB。缺省来源为 `chatgpt`。

| 模块 | 职责 |
| --- | --- |
| `src/domain` | 数据类型、状态转换、商店匹配、合并和单位规则 |
| `src/application` | 购物操作和事务编排 |
| `src/storage` | 原生 IndexedDB 结构、升级和事务生命周期 |
| `src/import-export` | 协议解析、导入预览、批次指纹、导出和恢复校验 |
| `src/ui` | 购物、待购池、商店管理和导入备份界面 |
| `tests` | 纯规则回归、浏览器测试和跨设备验收 |

第一阶段采用原生 ES 模块和 DOM，保留 TypeScript 类型声明与 JSON Schema。运行时和构建无 npm 依赖，适合独立静态发布。未来菜谱适配器输出相同 JSON 协议，传入 `source: { "type": "recipe", "ref": "recipeId:ingredientId" }`。当前保留引用，不按引用自动更新或覆盖需求。

## 分阶段实施

1. 定义状态、ID、备份及交换边界，再实现 IndexedDB、购物事务和导入预览。
2. 接入基础界面，验证刷新后勾选、未购回退、重复导入和完整恢复。用独立仓库的 GitHub Pages 工作流发布静态构建。
3. 第二阶段加入受限文字解析、输入确认、PWA 缓存和移动端体验。新增断网冷启动与升级后存储保留的测试。
4. 菜谱具备稳定食材 ID 后，通过适配器接入。以样例验证来源引用、用量和复购语义，再决定是否增加按外部引用的显式更新。
